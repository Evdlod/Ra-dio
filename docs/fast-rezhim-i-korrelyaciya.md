# Ra-dio fast: ускорение и журнал корреляции

Реализация предложений из [`optimizaciya-skorosti.md`](optimizaciya-skorosti.md)
в коде приложения. Только Wi-Fi Direct: без Wi-Fi Aware (NAN) и без Bluetooth/BLE.

Два результата этой итерации:

1. **Скорость** — быстрый путь доставки (UDP внутри группы + TCP с
   подтверждениями), событийный поиск, окна синхронизированного поиска,
   постоянная группа, адаптивные таймауты.
2. **Наблюдаемость** — структурированный журнал `corr_*.tsv`, по которому
   логи двух телефонов однозначно склеиваются, и скрипт для анализа.

---

## 1. Что включено и где выключается

Все переключатели — в `P2pConfig.java`, рядом с каждым есть комментарий.

| Возможность | Флаг | Значение по умолчанию |
|---|---|---|
| TCP-транспорт поверх группы | `ENABLE_P2P_SOCKET_TRANSPORT` | `true` |
| Быстрый путь — основной | `SOCKET_IS_PRIMARY_PATH` | `true` |
| Задержка TXT-резерва | `TXT_FALLBACK_DELAY_MS` | `1500` мс |
| UDP-канал внутри группы | `ENABLE_GROUP_LINK_CHANNEL` | `true` |
| Порт UDP-канала | `GROUP_LINK_PORT` | `8989` |
| Маячок presence | `GROUP_LINK_BEACON_MS` | `1000` мс |
| mDNS (NsdManager) в группе | `ENABLE_MDNS_ON_GROUP` | `false` (экспериментально) |
| Постоянная группа | `ENABLE_PERSISTENT_GROUP` | `true` (API 29+) |
| Диапазон группы | `PREFERRED_GROUP_BAND` | `GROUP_BAND_24` |
| Окна поиска | `SYNC_WINDOW_PERIOD_MS` / `SYNC_WINDOW_LENGTH_MS` | 5000 / 2000 мс |
| Приоритетный поиск | `PRIORITY_DISCOVER_GAP_MS` | `800` мс |
| Опрос пиров | `PEERS_POLL_INTERVAL_MS` | `2000` мс |
| Лестница повторов | `RETRY_LADDER_MS` | 1 / 2 / 4 / 8 с |
| Адаптивный RTO | `ADAPTIVE_RTO_MIN_MS` … `MAX_MS` | 300 … 8000 мс |
| Ретрансляция (C6) | `ENABLE_RELAY` / `RELAY_TTL` | `true` / `1` |
| Требовать Location Mode | `REQUIRE_LOCATION_FOR_DISCOVERY` | `true` |

Если что-то поведёт себя плохо на конкретной прошивке — выключается одним
флагом, без отката всего блока изменений.

## 2. Что именно изменилось в поведении

### 2.1 Первый контакт

| Приём | Было | Стало |
|---|---|---|
| A1 событийный поиск | каждые 4–8 с | приоритетный порог 800 мс по событиям |
| A2 фазовое разделение | `discoverPeers` + `discoverServices` подряд | при известных пирах — сразу `discoverServices` |
| A3 окна встречи | случайный момент | окна 2 с каждые 5 с, выровнены по UTC на обоих телефонах |
| A4 `requestPeers` | только по broadcast-событию | опрос каждые 2 с, без BUSY |
| A5 вход в группу | WPS PBC | SSID + пароль (API 29+) — без WPS-негоциации |
| A6 постоянная группа | нет | `enablePersistentMode(true)` — повторный контакт ~1 с |
| A7 удержание группы | `removeGroup` при потере | группа не рвётся; переподключение через 2 с |

Окна (A3) работают без переговоров: обе стороны считают
`t % SYNC_WINDOW_PERIOD_MS`, поэтому попадают в одни и те же интервалы.
Расхождение часов измеряется (`PeerClock`) и пишется в журнал полем `skew_ms`.

### 2.2 Доставка

Было: сообщение → TXT-слот (≤120 байт, DNS-кэш, `SLOT_RENEW_INTERVAL` 15 с) →
собеседник замечает через 0–8 с → ACK через 2 с.

Стало:

1. Сообщение сразу уходит по быстрому каналу: **UDP-датаграмма** внутри
   подсети группы (единицы мс), параллельно **TCP-кадр** с подтверждением.
2. Если ACK не пришёл за `TXT_FALLBACK_DELAY_MS` (1,5 с) — публикуется
   TXT-слот, как раньше. Пришёл — эфир не трогаем вообще.
3. Ретраи: 1 → 2 → 4 → 8 с; после исчерпания — принудительный TXT-резерв.
4. Keep-alive 5 с держит TCP живым против power-save.
5. RTO считается от измеренного RTT, а не берётся из константы 60 с.

Формат кадра (B4):

```
'R' 'D' ver type flags len_hi len_lo | payload | crc32
```

`payload` — строки с 2-байтовой длиной, текст в UTF-8: кириллица больше не
обрезается по границе байта, а битый кадр отсекается по CRC.

### 2.3 Гарантии

- Дедупликация по `msgId` (было) + фиксация дубликата в журнале событием
  `MSG_DUP` с указанием канала — видно, какой путь пришёл первым.
- Bloom-фильтр (128 бит, 32 hex-символа) в SYNC-записи вместо списка ID:
  собеседник точно узнаёт, что сообщения у него нет, и получает его
  немедленно, не дожидаясь минутного цикла.
- Ретрансляция через посредника: кадр с `ttl > 0` пересылается дальше один
  раз (`RelayCache`), поэтому дальность растёт без Bluetooth.
- Anti-entropy: при появлении собеседника сверка запускается сразу.

### 2.4 Поведение при выключенном радио

Если Wi-Fi выключен, Wi-Fi Direct находится в состоянии `DISABLED` и любая
команда supplicant'а возвращает `BUSY`. Раньше приложение в этом состоянии
продолжало опрашивать радио: в логе появлялись десятки строк
`discoverPeers failed: BUSY` / `FAILED to register main service: BUSY`, а
батарея расходовалась впустую.

Теперь перед любой командой проверяется готовность радио
(`isRadioReady()` = Wi-Fi включён **и** P2P не в `DISABLED`):

- поиск, регистрация `WFD_Main` и heartbeat при выключенном радио не
  выполняются вовсе; предупреждение пишется один раз на переход;
- повторы `discoverServices` с экспоненциальной паузой не запускаются —
  при `BUSY` от выключенного радио они бы жили вечно;
- у каждой цепочки поиска есть номер поколения: когда приходит broadcast
  о смене состояния или начинается новый цикл, старые цепочки молча
  завершаются, поэтому параллельных циклов не остаётся;
- `forceRefresh()` (он вызывается при каждом подключении к сервису) больше
  не создаёт второй проход, если поиск уже идёт;
- периодический цикл остаётся «дежурным»: как только радио вернулось, поиск
  возобновляется сам — даже если прошивка не прислала broadcast;
- в UI показывается диалог «Wi-Fi выключен» с кнопкой в системные настройки
  (один раз за запуск).

В журнале корреляции это видно как `DISC_REQ ... result=radio-off` с полями
`wifi=0/1` и `p2p=0/1`.

### 2.5 Вендорская совместимость

- **D1** — проверка Location Mode при старте сервиса и перед запуском в UI,
  с кнопкой «Открыть настройки». Без неё `discoverPeers` на MIUI/Funtouch
  возвращает пустой список без ошибки.
- **D2** — подсказки по автозапуску под бренд (MIUI/HyperOS, Funtouch/OriginOS,
  ColorOS/realme UI, EMUI, One UI).
- **D4** — детект `FEATURE_WIFI_DIRECT` и состояния P2P.
- **D5** — диапазон группы: 2,4 ГГц по умолчанию, 5 ГГц — флагом.
- **D7** — пока быстрый канал жив, отдельный ACK-сервис не публикуется:
  меньше сервисов → меньше BUSY.
- **D8** — `WFD_Main` обновляется heartbeat'ом каждые 5 с (чаще требуемых 10 с).

## 3. Журнал корреляции: как сопоставить два телефона

### 3.1 Файл

`Android/data/com.example.directtest/files/logs/corr_<deviceId>_<sessionId>.tsv`

Кнопка **«Файлы»** на экране диагностики выгружает журнал (шаринг).

Заголовок:

```
#ra-dio-correlation v1
#columns: t_utc_ms  t_iso  t_mono_ms  dev  sid  event  trace  peer  seq  detail
```

| Колонка | Смысл |
|---|---|
| `t_utc_ms` | абсолютное время (эпоха, мс) — по нему считается задержка между телефонами |
| `t_mono_ms` | монотонное время — для точных интервалов внутри одного телефона (не зависит от перевода часов) |
| `dev` | короткий ID телефона (8 hex) |
| `sid` | ID сессии приложения |
| `event` | код события |
| **`trace`** | **общий идентификатор цепочки**: `msgId` для сообщений, `probeId` для замеров |
| `peer` | короткий ID собеседника |
| `seq` | порядковый номер строки |
| `detail` | `key=value` через пробел: канал, задержка, попытка, `skew_ms` |

Ключ склейки — `trace`. Одно и то же сообщение на отправителе и на приёмнике
имеет один `msgId`, поэтому строки двух файлов соединяются напрямую.

### 3.2 События

| Событие | Где | Что означает |
|---|---|---|
| `START` | оба | старт менеджера/транспорта: версия протокола, модель, API |
| `ENV` | оба | окружение: `p2p`, `wifi`, `loc` (Location Mode), `persistent`, `band` |
| `DISC_REQ` / `DISC_RES` | оба | запрос поиска и его результат (`ok` / `BUSY` / `throttled` / `no-location`) |
| `PEERS` | оба | результат дешёвого `requestPeers` |
| `PEER_FOUND` | оба | первый контакт с приложением собеседника |
| `CLOCK` / `RTT` | оба | расхождение часов и задержка канала |
| `WINDOW` | оба | открылось окно синхронизированного поиска |
| `GRP_UP` / `GRP_DOWN` | оба | состояние группы Wi-Fi Direct |
| `LINK_UP` / `LINK_DOWN` | оба | быстрый канал (`udp-group` / `tcp`) |
| `MSG_SEND` | отправитель | сообщение принято приложением (слот, выбран ли быстрый путь) |
| `MSG_TX` | отправитель | отправлено в конкретный канал |
| `MSG_RX` | получатель | принято (канал, длина, RTT) |
| `MSG_DUP` | получатель | дубликат отброшен (какой канал пришёл вторым) |
| `ACK_TX` | получатель | подтверждение отправлено (канал) |
| `ACK_RX` | отправитель | подтверждение получено (канал, `rtt_ms`, попытка) |
| `RETRY` | отправитель | повторная передача (номер попытки и задержка) |
| `TXT_PUB` | отправитель | публикация TXT-слота: `published` или `skipped-acked` |
| `SYNC` | оба | сверка состояний, Bloom-фильтр, найденные пропуски |
| `RELAY` | посредник | кадр переслан дальше (`ttl`) |
| `ERR` | оба | ошибка с указанием места |

### 3.3 Типичная цепочка

Телефон A (отправитель):

```
... MSG_SEND  a1b2_7f3c_12  peer=b9d0e1f2  slot=0 fast=1 len=18
... MSG_TX    a1b2_7f3c_12  peer=b9d0e1f2  channel=udp-group bytes=42
... ACK_RX    a1b2_7f3c_12  peer=b9d0e1f2  channel=udp-group rtt_ms=6
```

Телефон B (получатель):

```
... MSG_RX    a1b2_7f3c_12  peer=a1b2c3d4  channel=udp-group rtt_ms=5
... ACK_TX    a1b2_7f3c_12  peer=a1b2c3d4  channel=fast sent=1
```

Задержка доставки = `MSG_RX.t_utc_ms(B) − MSG_SEND.t_utc_ms(A)`.
Задержка подтверждения = `ACK_RX.t_utc_ms(A) − ACK_TX.t_utc_ms(B)`.

### 3.4 Скрипт анализа

```bash
python3 tools/correlate.py corr_a1b2c3d4_*.tsv corr_b9d0e1f2_*.tsv
```

Скрипт (без зависимостей) склеивает журналы по `trace`, считает
`send → recv`, `recv → ack`, `send → ack`, печатает p50/p95, распределение
по каналам, случаи `MSG_DUP`, `TXT_PUB skipped/published`, потери и разброс
часов. Ничего не отправляет в сеть и не требует root.

## 4. Методика проверки на двух телефонах

1. Установить сборку на оба телефона, включить Location Mode, разрешить
   работу в фоне (подсказка по автозапуску — в логе при старте).
2. Запустить рацию на обоих, дождаться `PEER_FOUND` в журнале.
3. Отправить 20 сообщений по 10–20 символов с интервалом 2 с в каждую сторону.
4. Выгрузить `corr_*.tsv` с обоих телефонов (кнопка «Файлы»).
5. Запустить `tools/correlate.py` на двух файлах, сравнить с целевыми
   показателями:

| Метрика | Цель |
|---|---|
| Первый контакт | ≤ 3 с (повторный — ~1 с) |
| `send → recv` p50 | ≤ 1 с |
| `send → ack` p50 | ≤ 2 с, p95 ≤ 6 с |
| Доля `TXT_PUB skipped-acked` | ≥ 80 % (значит, быстрый путь работает) |
| `MSG_DUP` | допустимо, но доля ≤ 30 % (два канала) |

Если `TXT_PUB published` почти всегда — быстрый путь не поднялся: смотреть
`GRP_UP`, `LINK_UP`, `ENV loc=`, а также не блокирует ли прошивка UDP.

## 5. Что осталось за рамками

- **mDNS (NsdManager) на линке группы** — реализовано флагом
  `ENABLE_MDNS_ON_GROUP`, по умолчанию выключено: на части прошивок
  NsdManager игнорирует P2P-интерфейс. Замена — UDP-канал, ему всё равно,
  какой интерфейс выбран.
- **Local Only Hotspot (D6)** — не включён: требует отдельного разрешения и
  перезапуска радио; UDP-канал внутри группы покрывает ту же задачу быстрее.
- Офлайн-подпись и шифрование полезной нагрузки — вне задачи о скорости,
  но кадр (B4) для этого готов: есть поле `flags` и CRC.

## 6. Восстановление обнаружения (после регрессии быстрых проходов)

Быстрый режим однажды уже ломал главное — сам факт обнаружения. Ниже — что
именно было исправлено, и какие события теперь позволяют это увидеть в
журнале с двух телефонов.

### 6.1 Что было не так

| Симптом в журнале | Причина | Исправление |
|---|---|---|
| `DISC_REQ ... services_only=1` постоянно, `PEER_FOUND` нет | «лёгкий» проход включался по «кэш не пуст», а кэш предзаполняется сохранёнными устройствами | лёгкий проход только если `requestPeers` был успешен менее 10 с назад (`PEERS_FRESH_MS`) |
| Стек поиска не стартовал вообще | цепочка висела на колбэке `addLocalService`, который не вызывался при BUSY/выключенном радио | независимый старт `startDiscoveryStack(reason)` + сторож `ENSURE_STACK_DELAY_MS = 4 с` |
| `self_heal=radio-gate` через 15 с, дальше поиск идёт | прошивка не прислала `WIFI_P2P_STATE_CHANGED` | самовосстановление флага радио (`RADIO_SELF_HEAL_MS`) |
| `connect()` к сохранённому MAC, `GRP_DOWN connect-failed` | инициация группы по адресу из кэша прошлой сессии (MAC рандомизирован) | инициация только по адресам, увиденным в этой сессии **и** с маркером нашего приложения |
| Поиск «замолкал» после серии отброшенных цепочек | следующая итерация планировалась только из колбэка | сторож `DISCOVERY_SAFETY_MS = 10 с` и сводка `[HEALTH]` раз в 30 с |

### 6.2 Новые события для сопоставления двух телефонов

| Событие | Когда пишется | Что смотреть |
|---|---|---|
| `START` (`component=discovery-stack`) | стек поиска реально запущен | `reason`: `main-service-ready` — норма, `watchdog` — регистрация сервиса не ответила |
| `DISC_REQ` | каждый запрос поиска | `services_only=0` хотя бы раз в 10 с — иначе `discoverPeers` не выполняется |
| `ENV` (`self_heal=radio-gate`) | сброс залипшего флага радио | если есть — прошивка не присылает broadcast о состоянии P2P |
| `ENV` (`health=discovery`) | раз в 30 с | `peers`, `with_app`, `peers_age_ms`, `stack`, `group` — рост `peers` без `with_app` значит: телефоны видят друг друга, но сервис не публикуется |
| `WINDOW` | начало окна синхронизации | `period_ms` = 5000 при `pending=1`, 8000 в покое; значения должны совпадать на обоих телефонах |

### 6.3 Порядок разбора «не видят друг друга»

1. `START component=discovery-stack` есть на обоих? Нет — смотреть `ensure-discovery-stack` в `ERR`.
2. Растёт ли `peers` в `ENV health=discovery`? Нет — радио/локация, см. п. 2.5.
3. `with_app` больше нуля? Нет — `WFD_Main` не публикуется (`MAIN SERVICE REGISTERED` отсутствует).
4. `DISC_REQ services_only=1` подряд дольше 10 с — ошибка логики, присылать журнал.
