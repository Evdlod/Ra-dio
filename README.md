
# 📡 WiFi Direct Text Transceiver

> **Текстовая рация на вашем смартфоне — без интернета, без регистрации, без паролей**

## 🎯 Что это?

Используется только передатчик и приемник радиоволн, который встроен в смартфон.

Обычно они используется для подключения WIFI, но мы его используем только как устройство для отправки радиоволны в эфир.

Это приложение превращает обычный Android-смартфон в **цифровую текстовую рацию**.

Никакой инфраструктуры. Никаких серверов. Никакой регистрации. 

**Включил — и ты в эфире.**

Схема работы в одном предложении:

-   Два смартфона общаются напрямую по воздуху как настоящие радиостанции.
-   Один отправляет текст `«Привет!»`, второй отвечает `«Принял!»`.
-   Типичная дальность: 50–200 метров.
-   Задержка: 2–15 секунд.
-   Стоимость: 0 ₽, интернет не нужен.

## 🔬 Как это работает

### Аналогия с радиосвязью

Представьте старые добрые рации. Вы нажимаете кнопку PTT (Push-to-Talk), говорите в микрофон, отпускаете — и слушаете эфир. Все, кто на той же частоте, слышат вас.

**WiFi Direct работает примерно так же**, только:

-   вместо голоса — текст;
-   вместо радиочастоты — DNS-SD сервисы;
-   вместо «позывного» — Device ID (8 hex-символов);
-   вместо «Приём, как слышно?» — периодический heartbeat;
-   вместо «Принял, конец связи» — ACK.

| Классическая рация       | WiFi Direct Transceiver             |
|--------------------------|-------------------------------------|
| PTT (Push-to-Talk)       | Регистрация DNS-SD сервиса          |
| Голосовое сообщение      | TXT-запись с текстом                |
| Частота/канал            | Имя сервиса (`WFD_Main`, `WFD_Msg`) |
| Позывной                 | Device ID (8 символов)              |
| «Приём, как слышно?»     | Heartbeat каждые 5 секунд           |
| «Принял, конец связи»    | ACK (подтверждение доставки)        |

### Heartbeat — «Я на связи!»

Каждые 5 секунд устройство «выходит в эфир» и объявляет примерно следующее:

```
📡 WFD_Main:
id  = "a1b2c3d4" ← Мой позывной
sid = "695bf5e3" ← Когда я вышел в эфир (Session ID)
hb  = "42"       ← Счётчик передач
```

Другие устройства постоянно сканируют эфир.  
Если heartbeat от устройства не обновлялся более 20 секунд — станция считается «молчащей» и скрывается из активного списка.

## 📬 Архитектура сообщений

### Проблема

DNS-SD (Service Discovery) изначально не создавался для передачи пользовательских сообщений. Это «почтовые голуби» мира сетевых протоколов: передать текст можно, но нужна изобретательность.

### Решение: слотовая система

Для передачи используются **3 слота сообщений**:

-   `WFD_Msg0`
-   `WFD_Msg1`
-   `WFD_Msg2`

Каждый слот:

-   содержит максимум **одно** сообщение;
-   занят до тех пор, пока отправитель не получит ACK;
-   после получения ACK освобождается под следующее сообщение.

Пример:

-   `WFD_Msg0`: содержит сообщение `«Привет!»` для устройства с ID `b5c6…`, ждём ACK;
-   `WFD_Msg1`: свободен;
-   `WFD_Msg2`: свободен.

**Максимум одновременно ожидающих подтверждения сообщений: 3.**

Почему не больше:

-   ограничение размера TXT-записей в DNS-SD;
-   ограничение на количество одновременно публикуемых сервисов;
-   здравый смысл: сначала дождись ответа, потом шли следующее, чтобы не забивать эфир.

## 🔄 Жизненный цикл сообщения

### Сценарий 1: успешная доставка

Устройства:

-   A — отправитель;
-   B — получатель.

Пошагово:

1.  Пользователь на устройстве A вводит текст `«Привет!»`.
2.  A создаёт идентификатор сообщения, например `a1b2_695b_1` (формат: `позывной_sessionId_порядковыйНомер`).
3.  A публикует сообщение в слоте `WFD_Msg0`.
4.  B сканирует эфир и находит сервис `WFD_Msg0` от A.
5.  B считывает текст сообщения от A и сохраняет его в своей локальной истории.
6.  B публикует сервис `WFD_Ack`, указывая, какое сообщение подтверждает.
7.  A видит ACK с ID своего сообщения.
8.  A очищает слот `WFD_Msg0`. Статус сообщения: **доставлено**.

Типичное время от шага 3 до шага 8: **2–10 секунд**.

### Сценарий 2: получатель временно недоступен

Те же участники: A — отправитель, B — получатель.

Хронология:

-   **00:00** — A отправляет `«Привет!»`, создаётся `WFD_Msg0`. B в этот момент онлайн.
-   **00:05** — A ждёт ACK. B уходит «в сон» (выключен экран, WiFi-модуль засыпает).
-   **00:30** — на A срабатывает первый таймаут. Сообщение не удаляется, слот продлевается ещё на один интервал (расширение слота).
-   **00:45** — B «просыпается» (экран включён, WiFi снова активен).
-   **00:47** — B начинает сканировать эфир, находит слот `WFD_Msg0` с сообщением от A.
-   **00:48** — B отправляет ACK. A видит подтверждение.
-   **00:48** — A помечает сообщение как доставленное и освобождает слот.

Слот может удерживать сообщение **до 60 секунд** (несколько продлений), чтобы пережить кратковременный «сон» устройства-получателя.

## 🔄 Синхронизация — восстановление после сбоев

### Проблема

Ситуация:

1.  A отправил сообщение → B его получил ✅
2.  B отправил ACK → ACK **потерялся** ❌
3.  A уверен, что сообщение не доставлено.
4.  B уверен, что всё хорошо.

Нужен способ «свести показания» двух сторон.

### Решение: протокол SYNC

Каждую минуту устройства обмениваются «журналами связи» — сжатым описанием того, какие сообщения они **отправили** и какие **получили**.

Пример записи:

```
📡 WFD_Sync:
id   = "a1b2c3d4"                 ← Кто я
to   = "b5c6d7e8"                 ← Кому пишу
sent = "a1b2_1,a1b2_2,a1b2_3"     ← Какие сообщения я тебе отправлял
recv = "b5c6_1,b5c6_2"            ← Какие сообщения я от тебя получил
```

### Алгоритм восстановления по SYNC

Пусть:

-   A — отправитель;
-   B — получатель.

Шаги:

1.  Устройство A хранит у себя журнал:
    -   `sent`: какие сообщения оно отправило B;
    -   какие из них получили ACK, какие — ещё нет.
2.  Устройство B хранит у себя журнал:
    -   `recv`: какие сообщения оно получило от A;
    -   какие ACK на них уже отправляло.
3.  A публикует `WFD_Sync` c полем `sent=[msg_1, msg_2]`.
4.  B получает SYNC от A и сравнивает:
    -   свой `recv`, например `[msg_1, msg_2]`;
    -   с `sent` от A, `[msg_1, msg_2]`.
5.  Если списки совпадают — B понимает, что **получено всё**.
6.  B публикует свой `WFD_Sync` с полем `recv=[msg_1, msg_2]`.
7.  A получает SYNC от B, видит, что:
    -   `msg_2` есть в списке полученных у B;
    -   но у A на `msg_2` ACK ранее не пришёл.
8.  A делает вывод: «сообщение доставлено, просто ACK потерялся» — и помечает `msg_2` как **успешно доставленное через SYNC**.

### Сценарий 3: сообщение потерялось полностью

Теперь рассмотрим случай, когда сообщение не дошло до B вообще.

1.  A отправляет `msg_3` через слот `WFD_Msg0`.
2.  Из‑за помех или ошибки протокола B **никогда не видит** этот слот.
3.  На A истекает таймаут (до 60 секунд), слот освобождается, статус `msg_3`: «доставка неизвестна».
4.  Спустя примерно минуту A и B обмениваются `WFD_Sync`:
    -   A в `sent` указывает `[msg_1, msg_2, msg_3]`;
    -   B в `recv` указывает `[msg_1, msg_2]` (без `msg_3`).
5.  A, анализируя `recv` от B, понимает, что `msg_3` не дошло.
6.  A переотправляет `msg_3`:
    -   выбирает свободный слот `WFD_Msg*`;
    -   снова публикует сообщение.
7.  B получает сообщение, отправляет ACK.
8.  A получает ACK, помечает `msg_3` как **успешно доставленное**.

## 🆔 Session ID — защита от «призраков»

### Проблема

Устройство B перезапустило приложение:

-   Состояние сброшено.
-   Журнал сообщений пуст.
-   Локальные счётчики начинаются заново.

Но устройство A по‑прежнему помнит «старые» сообщения и может:

-   ждать от B ACK на старые сообщения;
-   считать, что B «забыло ему ответить».

Нужно понять, что у B **новая сессия**, а не просто «временный сбой».

### Решение: Session ID

**Session ID (sid)** — это метка времени запуска приложения, записанная в hex-формате.

Примеры:

-   `695bda95` — запуск в 14:00;
-   `695bf5e3` — запуск в 16:00 (число больше → сессия новее).

Поведение:

1.  До перезапуска:
    -   A знает, что у B `sid = 695bda95`.
2.  После перезапуска:
    -   B стартует заново и публикует `WFD_Main` с новым `sid = 695bf5e3`.
3.  A получает `WFD_Main` от B и сравнивает:
    -   новый `sid (695bf5e3)` с сохранённым старым `sid (695bda95)`.
4.  Так как `695bf5e3 > 695bda95`, A делает вывод:
    -   у B **новая сессия**;
    -   нужно:
        -   очистить историю сообщений, связанных с B;
        -   сбросить список ожидаемых ACK от B;
        -   сохранить новый `sid` как актуальный.
5.  Если вдруг приходит запись с `sid` **меньше** текущего:
    -   это считается устаревшим кэшем/мусором в сети;
    -   такие записи просто игнорируются.

## 📊 Технические детали

### Карта сервисов

| Сервис         | Назначение                  | Время жизни                         |
|----------------|-----------------------------|-------------------------------------|
| `WFD_Main`     | Heartbeat, статус, позывной | Постоянно (обновление каждые 5 сек) |
| `WFD_Msg0/1/2` | Слоты сообщений             | 30–60 сек (до получения ACK)        |
| `WFD_Ack`      | Подтверждения входящих      | 10–15 сек                           |
| `WFD_Sync`     | Синхронизация журналов      | ~30 сек                             |

### Диаграмма состояний сообщения (в словах)

**Основные состояния:**

-   **СОЗДАНО**  
    Сообщение только что сформировано в приложении.
-   **В СЛОТЕ (ждём ACK)**  
    Сообщение размещено в одном из слотов `WFD_Msg*` и доступно в эфире.
-   **EXTENDED (продлённый слот)**  
    Если в течение ~30 секунд ACK не пришёл, слот не удаляется сразу, а продлевается ещё на один интервал (пока общее время не превысит ~60 секунд).
-   **✅ ДОСТАВЛЕНО**  
    Получен ACK либо это установлено через протокол SYNC. Слот освобождён.
-   **РЕПОЗИТОРИЙ (ждём SYNC)**  
    Сообщение больше не в слоте (слот освободился), но A ещё не уверен, доставлено оно или нет. Окончательный статус уточняется при обмене `WFD_Sync`.
-   **СЛОТ ОСВОБОЖДЁН**  
    Слот больше не содержит сообщение. Если SYNC покажет, что сообщение не дошло — его можно будет переотправить.
-   **RESEND (переотправка)**  
    Если по результатам SYNC выясняется, что сообщение не было доставлено, оно повторно попадает в свободный слот и цикл «ждём ACK → SYNC» повторяется.

**Основные переходы:**

-   СОЗДАНО → В СЛОТЕ (публикация в `WFD_Msg*`).
-   В СЛОТЕ → ✅ ДОСТАВЛЕНО (получен ACK).
-   В СЛОТЕ → EXTENDED (истёк первый таймаут, получатель, возможно, спит).
-   EXTENDED → СЛОТ ОСВОБОЖДЁН (истёк второй таймаут, ACK так и не получен).
-   СЛОТ ОСВОБОЖДЁН → РЕПОЗИТОРИЙ (сообщение ждёт решения по SYNC).
-   РЕПОЗИТОРИЙ → ✅ ДОСТАВЛЕНО (SYNC показал, что получатель его видел).
-   РЕПОЗИТОРИЙ → RESEND → В СЛОТЕ (SYNC показал, что сообщение не дошло; переотправка).

### Дополнительный канал: сокеты поверх Wi-Fi Direct

По умолчанию выключен. Включается флагом `P2pConfig.ENABLE_P2P_SOCKET_TRANSPORT = true`.

Зачем: DNS-SD TXT — удобный, но тесный канал: одна запись ограничена 255 байтами, а supplicant агрессивно кэширует записи. С включённым флагом приложение дополнительно формирует P2P-группу и передаёт сообщения/ACK по TCP (порт 8988) — длина текста не ограничена, доставка подтверждается явно. Обнаружение и резервная доставка остаются на DNS-SD, дубликаты отсекаются по `msgId`.

Что нужно учитывать при включении:

- принимающая сторона увидит системный диалог «Принять запрос на подключение»;
- на части прошивок во время активного соединения приостанавливается поиск новых устройств;
- при выходе из зоны группа распадается — приложение само вернётся к TXT-обмену и повторит попытку.

### Скорость: как ускорить обнаружение и доставку

Разбор задержек по шагам, ограничения платформы, практики Google Nearby Connections, Briar и mesh-мессенджеров, а также приоритизированный план оптимизации — в документе [`docs/optimizaciya-skorosti.md`](docs/optimizaciya-skorosti.md).

Коротко: основное время уходит не на передачу, а на ожидание чужих циклов опроса. В документе — только технологии, доступные на Xiaomi, Redmi, vivo и подобных: сам Wi-Fi Direct, сокеты и mDNS внутри P2P-группы, Local Only Hotspot как резерв. Wi-Fi Aware (NAN) и Bluetooth исключены — NAN есть не на всех чипсетах, а Bluetooth проигрывает по дальности.

Основные резервы: событийный discovery, синхронизированные окна встречи, удержание persistent-группы (повторный контакт ~1 с вместо 3–9 с), немедленный ACK, короткие ретраи 1→2→4→8 с и Bloom-фильтр в SYNC. Ожидаемо: p50 ≈ 1–3 с вместо 8–12 с, при удержании группы — сотни миллисекунд.

### Если сообщения не доходят

1. **Проверьте часы** на обоих телефонах — расхождение больше 2 минут ломает фильтр устаревших сообщений.
2. **Включите Wi-Fi** — без него приём не работает (приложение предупредит).
3. **Разрешите работу в фоне** — на Xiaomi/Huawei/Samsung/Oppo агрессивный менеджер батареи убивает сервис; приложение предложит добавить себя в исключения при первом запуске.
4. **Длина текста.** Запись DNS-SD ограничена 255 байтами: кириллица занимает 2 байта на символ, поэтому длинное сообщение обрезается (в логах будет `text truncated`). Укладывайтесь в ~60 русских символов.
5. **Не выключайте экран во время отправки** — в спящем режиме часть прошивок приостанавливает Wi-Fi Direct.
6. **Смотрите логи** (кнопка «Логи»): там видно, на каком шаге затык — регистрация сервиса, `BUSY` в discovery или отсутствие ACK.

-   🎮 Игры на местности
-   👥 Координация небольших групп

**Не подходит:**

-   Дальние расстояния (**\> 200 м**)
-   Критически важные сообщения (требующие гарантированной мгновенной доставки)
-   Передача файлов, изображений и больших объёмов данных

## 📋 Приложение: Формат протокола

### WFD\_Main (Heartbeat)

```
id  = a1b2c3d4     # 8 символов hex, ID устройства
sid = 695bf5e3     # Session ID (hex timestamp запуска)
hb  = 42           # Номер heartbeat
t   = 1705123456   # Unix timestamp
v   = 4            # Версия протокола
ack = xyz_1,xyz_2  # Подтверждения (опционально)
```

### WFD\_Msg\* (Сообщение)

```
id  = a1b2c3d4          # Отправитель
mid = a1b2_695b_1       # ID сообщения (уникальный)
msg = Привет!           # Текст (до 100 символов)
to  = b5c6d7e8          # Получатель (опционально)
s   = 0                 # Номер слота (0, 1 или 2)
t   = 1705123456        # Timestamp
sid = 695bf5e3          # Session ID отправителя
```

### WFD\_Ack (Подтверждение)

```
id  = b5c6d7e8      # Кто подтверждает
ack = a1b2_695b_1   # Какое сообщение подтверждено
t   = 1705123456    # Timestamp
sid = 695bf5e3      # Session ID
```

### WFD\_Sync (Синхронизация)

```
id   = a1b2c3d4                 # Кто отправил SYNC
to   = b5c6d7e8                 # Кому адресовано
sent = a1b2_1,a1b2_2,a1b2_3     # Мои отправленные сообщения
recv = b5c6_1,b5c6_2            # Сообщения, полученные мной от адресата
t    = 1705123456               # Timestamp
sid  = 695bf5e3                 # Session ID
```

## 🚀 Быстрый старт

1.  **Установи** приложение на устройство с Android 5.0+.
2.  **Включи** WiFi (подключаться к точкам доступа не нужно).
3.  **Выдай** разрешения (в частности, Location — он обязателен для работы WiFi Direct).
4.  **Подожди пару секунд** — в списке появятся другие пользователи поблизости.
5.  **Выбери** собеседника и **отправь** первое сообщение.

Ключевые свойства:

-   Никакой регистрации.
-   Никаких паролей.
-   Никаких QR-кодов.
-   Никакого интернета.

Просто включай «текстовую рацию» и общайся с людьми вокруг —  
**бесплатно и без SMS**.
